## Share/return defect and limits of the diagnosis

A focused regression reproduced a concrete defect in the previous code: an own event share triggered two scroll corrections while the picker still covered the conversation, consuming the deferred correction on the hidden route. That regression failed before the change and passes afterwards.

The conversation now ignores zero/hidden viewport and composer measurements, freezes keyboard-driven adjustment while covered, and retains the actual pending-new-message correction until visible. Returning while reading history, without a new own message, does not issue an unconditional scroll-to-latest. The native latest offset still includes the real negative composer/keyboard inset.

A second focused regression exposed another ordering defect: the returning viewport's `onLayout` consumed that correction before the shared-event content measurement. The failing sequence was reproduced in the callback test. Viewport layout may now position the list but does not consume the final content-layout correction. All 23 focused keyboard/scroll/cover/menu/history checks passed after this final correction.

This proves a code-level lifecycle defect and its correction. It does **not** prove that every physical iPhone blank-area or unbounded-card symptom has the same cause. The submitted recording is visual evidence, not a captured native layout trace.

The user's later screenshot confirms the problem persists on their device: a tall grey rectangle labelled “Open outing” extends beyond the visible conversation. Browser ResizeObserver measurements, the real local API flow and Yoga layout tests do not reproduce that growth. The iPhone inspector endpoint on the user's 8081 server remained empty (`[]`, and one timeout), so no current UIKit geometry trace was obtained. **The reported bug is accepted; its native cause and the final correction are not yet physically verified.**

The screenshot narrowed inspection to the shared event's associated-outing action. Although it was styled as a plain text/ghost action, `ActionButton` still created an iOS `GlassView` with effect `none` and a growing inner control. The installed native implementation mounts those children inside `UIVisualEffectView.contentView`; ordinary Yoga Views do not exercise that UIKit path. Only this plain in-card action was changed to the existing `OutingPressable`, retaining its label, 44-point target, disabled state and behavior. Global Glass buttons, the navbar, the photograph and its geometry were not redesigned. Removing this unnecessary native host is a scoped correction/isolation, not proof from the screenshot that generic flex growth caused the defect.

Three further regressions render the real conversation item with an actual associated choosing-event plan, deriving “Open outing” from the group rather than injecting the label. They verify separate photo/event and action/outing navigation, no implicit creation, and bounded full-message Yoga layout through 652 → 0 → 652 → 328 viewport changes at widths 320/390/430. The associated browser path then passed 44 targeted assertions with no runtime errors; both senders' and recipients' rows remained stable after settling and returning from the outing. These checks still do not execute UIKit child mounting.
